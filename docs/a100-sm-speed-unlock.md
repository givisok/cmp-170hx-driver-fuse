# A100-зашитая CMP 170HX: возврат полной SM-производительности

Разбор самой интересной проблемы этого стенда: карта, перестращенная под A100 PCIe 80GB
(`10de:20b5`), после любого ребута работала, но считала в 23 раза медленнее соседей.

| | matmul 8192² fp16 | SM-клок | мощность под нагрузкой |
|---|---|---|---|
| CMP-пара (`10de:20c2`) | ~5.1 мс ≈ 213 TFLOPS | 1410–1470 MHz | норма |
| A100-карта, сток | **119 мс ≈ 9.2 TFLOPS** | 1410 MHz, util 100 % | **83 В** |
| A100-карта, `cmp_a100_ss=1` | 5.14 мс ≈ 214 TFLOPS | 1410 MHz | норма |

Мелкие кернелы на стоке шли с нормальной задержкой — то есть SM-клок настоящий, а задушена именно
пропускная способность тяжёлых кернелов. В vLLM (PP=3) конвейер постоянно ждал этот рэнк, поэтому
«модель стала сильно медленнее».

## 1. Механизм cmpunlocker (что такое «payload» и «PLM»)

Драйвер `open-gpu-kernel-modules` на Turing+ грузит GSP так: хост кладёт подписанный пакет
прошивки в WPR-регион видеопамяти, заполняет структуру **WPR meta** и запускает на falcon SEC2
загрузчик (**booter**), который проверяет подпись, поднимает WPR2 (write-protected region) и
передаёт управление RISC-V. Код загрузки — `kgspBootGspRm` / `kgspBootstrap` в
`src/nvidia/src/kernel/gpu/gsp/kernel_gsp.c` и `arch/turing/kernel_gsp_{tu102,booter_tu102}.c`.

Патч `cmpunlocker/driver/patches/sec2-postbl-plm-ss-cfg.patch` встроился в этот поток:

* `_kgspCreateSignatureMemdesc` вместо стоковой подписи кладёт в sysmem **payload** размером
  0xf800 байт (`_kgspSec2PostblTimingFillPayload`) — фрагмент кода для falcon'а, который делает
  ровно одну привилегированную запись в регистр: `writeAddr ← writeValue`.
* `kgspSec2PostblTimingRefillPayload(pGpu, pKernelGsp, addr, value)` наполняет payload, после
  чего `kgspExecuteBooterLoad_HAL(...)` запускает загрузчик. Тот выполняет payload и
  останавливается с кодом в mailbox0 **0x31** — для этих запусков это норма, регистр записан.
* Так открываются **PLM** (privilege level masks) — регистры, определяющие, кому можно писать
  в тот или иной блок. После открытия PLM хост может писать в защищённые регистры сам.
* Стоковая подпись сохраняется (`pStockSignatureData`) и перед настоящей загрузкой GSP
  восстанавливается (`kgspSec2PostblTimingRebuildStockSignature`) + `kgspPopulateWprMeta_HAL`.

Для CMP-карт цикл такой: 12 PLM → запись SS0/SS1 (SM speed) → CFG1/LMR (геометрия памяти) →
SM-RECONFIG → PCIe-секция (ещё ~40 запусков payload) → восстановление подписи → загрузка GSP.

## 2. Ключевой нюанс: WPR2

Каждый запуск загрузчика оставляет **WPR2 «поднятым»**: `NV_PFB_PRI_MMU_WPR2_ADDR_HI`
(`0x1fa828`) становится ненулевым (у загруженной карты — `0x13fee00`). Следующий запуск
загрузчика из такого состояния заканчивается сразу ошибкой, а без восстановления — вообще
зависает. Поэтому перед каждым запуском патч пишет в `WPR2_ADDR_LO/HI` сохранённые значения
(`HI = 0`, «down»). `kgspIsWpr2Up_TU102` смотрит именно на `HI`.

Но эти два регистра сами закрыты PLM — `WPR_CFG` (`0x1fa7cc`) и `WPR` (`0x1fa7c4`). Пока они
не открыты, обычная запись в WPR2 **молча отбрасывается**.

## 3. Две неудачные попытки

Журналы — в [boot-logs/](boot-logs/).

**Minimal-попытка: Booter 0x5.** Открывали только PLM `FEAT` (чтобы записать SS0/SS1), a WPR2
восстанавливали обычной записью — а её PLM `WPR_CFG`/`WPR` ещё не были открыты, и она молча
отбрасывалась. WPR2 оставался поднятым, и настоящий booter выходил с **0x5** через 5 мс.
Четыре попытки — probe карты падал, хост продолжал работать.

**Полный CMP-цикл: falcon зависает (0x65).** Для `0x20b5` включили весь цикл. 12 PLM открылись
нормально, затем патч записал SS0/SS1 + CFG1/LMR + SM-RECONFIG, и первый же PCIe-запуск
загрузчика завис: falcon не остановился, 60-секундный таймаут, `status 0x65, mailbox 0x31`
(значение от прошлого успешного запуска). Хост тоже выжил. Триггер — не SS: при фиксе SS
записываются и загрузка идёт нормально. Остаются CFG1/LMR (у A100 стоковое `LMR = 0x28b`, цикл
пишет `0x20b`) или SM-RECONFIG; точно не выясняли — на рабочем пути их просто нет.

## 4. Фикс: параметр `cmp_a100_ss`

Всё в `cmpunlocker/driver/patches/` (генерируются `a100/mkpatches.py`, см. [a100/README.md](../a100/README.md)):

* `a100-ss-param.patch` — объявляет в `kernel-open/nvidia/nv-pci.c` параметр модуля
  `cmp_a100_ss` (int, 0444). Без записи в modprobe.d он равен 0 — карта грузится стоком, и
  загрузка не может из-за него «зависнуть».
* `sec2-postbl-plm-ss-cfg.patch` — гейт `_kgspSec2PostblTimingEnabled` теперь истинен и для
  `0x20B5`, если `cmp_a100_ss != 0`; в основной блок добавлен «A100-блок» до цикла PLM:
  1. печать стоковых SS0/SS1 и PLM;
  2. по одному запуску payload: открыть `WPR_CFG` → `WPR` → `FEAT`;
  3. восстановить WPR2 и напечатать readback (сразу видно, сработало ли);
  4. если `cmp_a100_ss == 1` — записать `SS0 = 0x88888888`, `SS1 = 0x8`;
  5. восстановить стоковую подпись, перезаполнить WPR meta;
  6. `goto a100Done` — мимо CMP-шных CFG1/LMR, SM-RECONFIG и PCIe-секции.
* `booter-verify.patch` — для `0x20B5` печатаются код завершения загрузчика и верификация
  PLM/SS0/SS1/CFG1/LMR после загрузки. (Значения `CFG1=0x02779000`, `LMR=0x28b` — сток карты.)

* **Контроль (`cmp_a100_ss=2`)** — то же самое без записи SS: загрузка проходит
  (`normal BooterLoad status=0x0`), значит дело было именно в SS, а не в потоке загрузки.

## 5. Проверка

Холодная загрузка с `options nvidia cmp_a100_ss=1` в `/etc/modprobe.d/cmpunlocker-a100-ss.conf`,
затем ребут с восстановленным автозапуском контейнера (CT 101, `onboot=1`):

* `journalctl -b -k | grep -E "GPU2.*(A100|BooterLoad)"` — рабочий путь, статус 0x0;
* nvidia-smi: 3× 81920 MiB, Gen3 x16/x16/x8;
* замер `bench/gpubench.py` после холодной загрузки: 212.1 / 213.7 / **214.0** TFLOPS;
* vLLM на трёх картах поднялся сам (01:30:31 reboot → 01:36:16 ready, ~5.7 мин), запрос проходит.

## 6. Урок из этой ночи

Дважды казалось, что хост «крашится» — по журналу это были обычные загрузки, где карта не
проходила probe, а ядро доживало до конца. Сначала читаем `journalctl -b -1 -k`, потом делаем
выводы.

## 7. Не менять на этой карте

* `CFG1/LMR` и SM-RECONFIG — полный CMP-цикл для `0x20b5` вешает загрузчик.
* «Minimal»-версия без открытия `WPR_CFG`/`WPR` — гарантированный Booter 0x5.
* Стоковые `SS0/SS1` равны `0x00000000`, стоковый `LMR = 0x28b` — при откате возвращать именно их.
